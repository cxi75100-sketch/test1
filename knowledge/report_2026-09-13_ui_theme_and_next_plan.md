## 一、已更新内容

- 新增统一 `AppPalette`，集中维护海军蓝、珊瑚、薄荷、亮黄以及明暗表面色。

- 日间状态栏使用深色图标，夜间使用浅色图标；底部系统导航栏同步主题。

### 2. 首页与空状态

- AppBar 增加识别度明确的“课”字标、课程新增与设置入口。
- 今日/整周切换改为高辨识信息板，选中态与非选中态层级明确。
- 今日信息卡展示日期、周次、课程数与学期进度。
- 无课状态增加 `FREE DAY` 卡与「查看整周 / 新增课程 / 教务导入」快捷入口，避免只有一行空文案。

### 3. 整周课表标签

- 修复整周页面使用独立 `_GridCourseCard`、没有随通用课程卡换肤的问题。
- 整周窄卡与详情页共用 `courseGradientColors()`；窄卡使用较低渐变强度，兼顾统一性和连续浏览的疲劳控制。
- 标签保留课程名、节次、时间、教室和教师；超矮叠课使用专用紧凑布局。
- 日列在日间使用暖中性色，在夜间使用抬升深蓝灰；上午和下午/晚间仍按固定格位呈现，未破坏“一屏五门课、列内不滚动”的既有约束。

### 4. 主题设置

- 设置页新增「外观」分区，包含：
  - 跟随系统；
  - 日间；
  - 夜间。
- 偏好复用现有 Drift `settings` 表，键为 `theme_mode`，没有增加数据库迁移。
- 默认值为跟随系统，非法或旧值安全回退为跟随系统。
- 三个选项具备 selected 语义和稳定测试 Key，方便无障碍与回归测试。

## 三、实施过程中遇到的问题

### 1. 背景方向第一次判断错误

最初为了强化“手账感”加入纸张网格和圆点，即使降低透明度，重复纹理仍会持续抢占注意力。用户明确指出背景丑之后，本轮没有继续微调透明度，而是删除整套重复纹理。

结论：手账识别度应由信息卡、标签、排版和少量非对称装饰承担，不能依赖铺满全屏的纹理。

### 2. 整周标签拥有独立实现

通用 `CourseCard` 完成换肤后，整周课表仍显突兀。原因不是颜色参数遗漏，而是整周使用独立 `_GridCourseCard`，并受固定格高和超矮叠课约束。

处理：保留独立布局，但提取共享的课程渐变函数，使详情和整周共享视觉规则，而不是强行复用不适合窄列的组件。

### 3. 夜间模式不能只改根主题

旧页面存在大量 `AppPalette.paperBright`、`AppPalette.ink` 等固定明色引用。如果只给 `MaterialApp` 增加 `darkTheme`，会出现亮白卡片、暗底深字和边界消失。

处理：核心页面的表面、边界、正文和弱信息逐步改为 `ColorScheme` 语义色；品牌渐变、亮黄节次章等有明确对比关系的元素继续保留固定品牌色。

### 4. 模拟器发现系统栏对比问题

首轮日间实画中，状态栏仍显示白色图标，在浅色背景上几乎不可见。Widget 测试与普通页面截图不容易发现这一点。

处理：在明暗主题的 `AppBarTheme.systemOverlayStyle` 中分别设置状态栏和系统导航栏的颜色/图标亮度，并重新安装复验。

### 5. 中文路径下 Flutter analyze 异常

在 `D:\桌面\课程表` 直接运行 `flutter analyze` 仍会触发 analysis server 的 LSP JSON `Unterminated string`。这不是本轮代码错误。

处理：沿用项目既有方案，将目录映射为 `R:`，在 `R:\` 完成 analyze、test 和 build。

### 6. 全目录格式化造成无关差异

一次 `dart format lib` 触碰了 7 个与 UI 无关的导入模块文件，只产生换行格式变化。

处理：提交前逐项核对并恢复这些无关格式化差异，最终待提交文件只保留 UI、主题、测试和知识库范围。后续只格式化明确改动的文件列表。

### 7. 桌面窗口截图不可靠

Computer Use 首次截取 Android Emulator 窗口时混入了其他窗口画面，不能作为视觉证据。

处理：改用 `adb exec-out screencap` 获取设备帧缓冲截图，并配合 UIAutomator 与 logcat 交叉核验。

## 四、当前仍存在的风险与不足

### P0：需要用户继续判断的视觉项

- `UNVERIFIED`：目前风格是否已达到用户期望，而不只是技术正确。
- `UNVERIFIED`：有真实满课数据时，不同课程渐变连续出现是否仍然耐看。
- `UNVERIFIED`：夜间在真机 OLED 低亮度环境下，深蓝层级是否过暗或局部彩色是否偏亮。

### P1：页面覆盖不完整

- 核心页面已接入主题；课程编辑表单、导入风险门、导入预览、大批量差异弹窗主要依赖全局 ThemeData，尚未逐页做夜间模拟器实画。
- Android 桌面小组件已有跟随系统的夜间资源，但它与 App 新色板不是同一套 token，视觉一致性尚未专项复核。

### P1：视觉规范仍需固化

- 当前已有颜色与组件实践，但还没有单独的 UI 规范文档记录圆角、间距、字号、阴影和明暗对比规则。
- 部分品牌色仍直接写在页面中；继续迭代时可能再次发生局部颜色漂移。

### P2：平台与无障碍

- 尚未验证系统大字体、显示缩放、色彩校正和高对比模式。
- iOS 未实机验证，系统栏和字体表现只能视为未验证。

## 六、推荐优先级

推荐顺序为：

1. **先完成阶段 A 的视觉验收与规范固化**；
2. **再完成通知/小组件/日期语义的版本收口**；
3. **然后启动多校阶段 0～1 的无行为重构**；
4. 获得第二所学校真实接口与校历后，再进入多校阶段 3。

理由：现在立刻做多校会同时改变数据模型、设置页和课表布局，容易让刚建立的 UI 基线再次漂移。先把视觉系统和当前单校版本固定下来，再扩展架构，返工成本更低。
